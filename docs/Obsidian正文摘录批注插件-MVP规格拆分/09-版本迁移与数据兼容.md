# 09-版本迁移与数据兼容

## 核心原则

批注数据是长期资产，版本迁移必须从 MVP 开始设计。

核心原则：

> 读到哪个 sidecar，就迁移哪个 sidecar。

也就是 lazy migration。

## schemaVersion

sidecar 必须带 `schemaVersion`。

文档级结构：

```ts
interface SideCommentDocument {
  schemaVersion: 1;
  filePath: string;
  fileHash: string;
  updatedAt: string;
  comments: SideComment[];
}
```

使用 `schemaVersion`，不要只写 `version`。

原因：

- 避免和插件版本混淆。
- 便于判断数据结构迁移。
- 便于未来做迁移链。

## 启动不全库迁移

插件启动时不能扫描全库 sidecar。

不做：

- 启动时遍历 `.obsidian-side-comments/files/`
- 启动时批量升级所有 JSON
- 启动时全库备份

原因：

- 用户可能有几十万篇笔记。
- sidecar 文件数量可能非常大。
- 启动迁移会拖垮 Obsidian。

## Lazy Migration

打开某篇文档时：

```text
读取 sidecar -> 检查 schemaVersion -> 如旧版本则迁移 -> 写回新版本
```

只迁移当前加载的 sidecar。

不打开的文档不迁移。

## 迁移必须幂等

每个 migration 必须可重复执行。

要求：

```text
运行一次和运行多次结果一致
```

原因：

- 防止迁移中途失败后数据半升级。
- 防止重复加载同一 sidecar 时产生重复字段或重复数据。
- 防止用户手动恢复备份后再次触发迁移出错。

## 迁移前备份

每个 sidecar 第一次迁移前，写一份备份。

备份路径：

```text
.obsidian-side-comments/backups/schema-v1-to-v2/ab/abxxxx.json
```

规则：

- 只备份被迁移的文件。
- 不做全库备份。
- 同一个 sidecar 同一个迁移版本只备份一次。
- 备份失败时，不执行迁移写回。

## 迁移链

迁移使用链式执行。

示例：

```ts
const migrations = {
  1: migrateV1ToV2,
  2: migrateV2ToV3,
  3: migrateV3ToV4,
};
```

如果读到 v1 数据，而当前 schema 是 v4，则按顺序执行：

```text
v1 -> v2 -> v3 -> v4
```

不允许跳版本直接改。

## 降级兼容

支持向前迁移，不支持降级写入。

说明：

> 新版插件可以读取旧数据并升级，但不保证新数据被旧版插件正确读取。

如果用户降级插件，旧版插件可能无法识别新版 schema。

## manifest schema 信息

`.obsidian-side-comments/manifest.json` 记录全局元信息。

结构：

```json
{
  "schemaVersion": 1,
  "pluginVersion": "0.1.0",
  "updatedAt": "2026-05-20T00:00:00.000Z"
}
```

说明：

- `schemaVersion` 表示当前插件写入的新 sidecar schema。
- `pluginVersion` 表示最后写入 manifest 的插件版本。
- `updatedAt` 表示 manifest 更新时间。
- manifest 不作为全库索引。
- manifest 不要求扫描全部 sidecar。

## 迁移失败处理

如果迁移失败：

- 不覆盖原 sidecar。
- 保留备份。
- 当前文档侧边栏显示读取失败状态。
- 提示用户检查 `.obsidian-side-comments/`。
- 不影响其他文档。

建议错误文案：

```text
批注数据迁移失败，已保留原始数据和备份。
```
